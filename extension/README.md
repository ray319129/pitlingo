# PitLingo — Chrome 擴充功能（MV3）

對應 `handoff.md` 路線圖的 **P2**。目前是 `v0.4.2`，功能面已與 userscript 對等。

---

## 與 userscript 的關鍵差異

| | Userscript | 擴充功能 |
|---|---|---|
| 執行環境 | 頁面環境（`unsafeWindow`） | **MAIN + ISOLATED 雙 world** |
| 取得字幕 | 整軌預抓 → Worker 注入 → DOM | **同左**（v0.4.0 起三層齊備） |
| 翻譯由誰執行 | 直接呼叫 Anthropic（自備金鑰） | **後端 `/v1/translate`** |
| contentId | 攔截網路請求 | **`performance.getEntriesByType('resource')`** |
| API 金鑰 | 存在使用者本機 | **不存在，後端保管** |
| 網路請求 | userscript 直接發 | **全部經過 service worker** |
| 共用快取 | 讀 + 主動上傳整包（需 ADMIN_TOKEN） | 讀 + **由後端代寫**（見下） |

### 取得字幕的三層（與 userscript 相同，自動降級）

```
第 1 層  整軌預抓
         worker 攔到的 m3u8 → 字幕清單 → 全部 VTT 分段 → 一次全翻
              ↓ 拿不到清單
第 2 層  Worker 即時攔截
         inject.js 注入 blob worker → 攔它的 fetch/XHR → BroadcastChannel
              ↓ 注入失敗
第 3 層  DOM 逐句翻譯
         字幕出現在畫面上才翻（最貴，會跳句）
```

**任何一層失效都只是變貴，不會壞掉。**

### 為什麼一定要 Worker 注入

只讀 DOM 的話提前量是 **0**——字幕出現在畫面上我們才知道有這句，翻譯來回
1~3 秒而轉播每 3~4 秒一句，永遠追不上。（v0.1.x 就是這樣，實測明顯跳句。）

播放器本來就會**提前約 50 秒**下載字幕分段。攔到那些分段，提前量就回來了。

> **v0.2.x 曾經試圖用 PLAY API 繞過注入，八個版本全部失敗**（見 handoff 7.7）。
> 而且 F1TV 掛有 Imperva 機器人防護（`reese84`），反覆試錯會被擋。
> Worker 注入反而**不產生任何額外的網路請求**——它只是搭播放器自己的請求便車。
> v0.4.0 已把 PLAY API 那整套（權杖掃描、cookie 讀取）移除，`cookies` 權限一併拿掉。

### 整軌預抓的入口

v0.3.x 只有第 2 層，因為以為「沒有 PLAY API 就拿不到 master m3u8」。
其實 **worker 本來就會抓 m3u8**，只是當時的 hook 只送 VTT 不送 manifest。
v0.4.0 補上之後，第 1 層就通了：

```
inject.js 攔到 m3u8
  → 路徑 1：直接攔到字幕清單（最穩，body 已在手上）
  → 路徑 2：從 master 的 #EXT-X-MEDIA:TYPE=SUBTITLES 解析
  → 全部 VTT 分段 → 批次翻譯 → 存進共用快取
```

**直播**：字幕清單是滑動視窗，每 20 秒重抓補新分段。
觀眾本來就落後 live edge 20~40 秒，所以仍有餘裕。

### 共用快取：擴充功能有在貢獻

擴充功能沒有上傳按鈕（使用者不該持有 `ADMIN_TOKEN`），但**譯文確實會進共用快取**：
後端的 `/v1/translate` 每次翻完都會把結果寫回該片的 bundle。

所以有兩條灌注路徑：

| 路徑 | 誰做 | 時機 |
|---|---|---|
| `POST /v1/subs` 整包上傳 | 你，用 userscript 當管理員工具 | **賽前**就能灌滿 |
| `/v1/translate` 順手寫回 | 任何擴充功能使用者 | 邊看邊累積 |

第一個看某支影片的人負擔全部翻譯成本，後面的人零成本。

⚠️ **頁面上沒有 `<video>`、也拿不到影片編號時一句都不送（2026-11-03）**：R19 正賽有觀眾停在賽事頁（`/page/12332/…`）找連結，
頁面上的文字 15 秒後照樣被送去翻譯，281 句進了 `misc`、算在那位觀眾的授權上。現在直接丟掉並計數
（診斷寫「※ 頁面沒有影片、沒送出 N 句」）；有影片但拿不到編號（從活動頁進去看）照舊等 15 秒再送。測試：`check-extension-behavior` 2n。

## 專案結構

```
extension/
  manifest.json              權限、進入點
  src/
    shared/
      normalize.js           clean() 與 normKey() ⚠️ 必須與後端、userscript 一致
      defaults.js            內建設定、預設選項、遠端設定合併
    background/
      sw.js                  唯一對外通訊處：後端 API、設定與 bundle 快取
    content/
      main.js                contentId、字幕讀取、疊字顯示
      overlay.css            疊字層樣式
    options/
      options.html/.js/.css  設定頁（同時當作工具列彈出視窗）
```

### ⚠️ `normKey()` 是兩份程式碼之間的硬性契約

`extension/src/shared/normalize.js`、`backend/src/parts/`
兩處的 `normKey()` 必須**完全一致**。不一致的話同一句話會算出不同的鍵，
共用快取整個失效——而且**不會報錯，只會默默重翻**。改動時兩邊要一起改（userscript 2026-10-28 已封存，不再列入）。

### 管理版的收割（v0.37.0，取代 userscript 的收割選單）

1. `chrome://extensions` 載入 `dist/pitlingo-admin`（先停用正式版／測試版）
2. 圖示 → 設定頁最下面「🚜 管理版：收割」貼上 **HARVEST_TOKEN** → 儲存（會先驗證，錯的不存）
3. 打開 F1TV，按 **Alt+Shift+J** 開控制面板（佇列在跑時會自動打開）

| 按鈕 | 等於 userscript 的 |
|---|---|
| 🚜 依計畫收割本頁 | 「依後端計畫收割本頁」：刮本頁連結 → 後端挑出缺的、到時間的 → 排進佇列開跑 |
| 🌐 全季收割 | 同名：本季頁 → 逐站刮連結 → 一次交給後端計畫 |
| ⏯ 開始／暫停 · 🔁 重跑失敗 · 🗑 清空佇列 · 🤖 自動開始 | 同名 |
| 🩹 補網址後綴 | 「補回缺少網址後綴的影片」 |
| 🎯 重收這一支（v0.37.1） | 「立即整軌預抓」：後端說已完整也照樣重抓、重新蓋章 |

- 每一支：整軌預抓 → 翻譯經過後端（成本記在 `harvest`，另外熔斷，超過回 E80）→ **翻譯真的結束後**蓋完整標記（`POST /v1/subs`，帶整支譯文與分段數，版本 `ext-0.37.0`）→ 下一支
- **翻譯清單的時間軸（2026-11-06，後端 v5.95）**：重播整軌預抓時，每個分段的起點＝清單裡前面所有分段的 EXTINF 加總，每句的秒數＝`cueVideoSec`（cue 落在分段範圍內＝絕對時間直接用；落在 0～分段長度＝相對時間加分段起點；都不像＝退回分段起點，誤差最多一個分段）。同一句取最早那次，蓋章時以 `times` 跟譯文一起送，**不多寫 KV**。直播與「後端已完整、跳過預抓」的影片不會送；舊影片要有時間就在後台按「撤銷完整標記」或用 🎯 重收（翻譯都命中快取，不花錢，但會再抓一輪分段）。全部包在 `@admin-only`，正式版／測試版沒有（`--check` 擋 `harvestTimes|cueVideoSec`）。測試：`tools/check-line-times.js`
- 不完整（有放棄的句子，或沒譯文的超過 max(20, 2%)）不蓋章、記成失敗，用「重跑失敗」補
- 佇列接手的頁面抓取改全速（6 條並行、60ms、不讓路給影片；v0.37.2）。自己開來看的影片仍是觀眾版節奏
- 單支逾時看「多久沒進度」：5 分鐘沒有任何進度記成失敗，另有 120 分鐘硬上限（v0.37.2；以前固定 15 分鐘，正賽抓不完）
- **「這支沒有字幕」要有證據（2026-11-03）**：只有攔到 master、裡面確實沒有字幕軌（`snapshot().subTrack === 'none'`）才在 90 秒後記**完成**；沒看到 master 或有字幕軌卻拿不到清單，3 分鐘後記**失敗**（可以「重跑失敗」）。以前 90 秒沒清單一律記「完成：沒有官方字幕」——R19 排位重播就這樣被記成完成、之後不會再收
- 背景分頁的計時器會被 Chrome 節流：把收割分頁拉成獨立視窗並保持可見
- ⚠️ 設了收割權杖，**所有翻譯都算收割成本**（拿它看直播也是）。自己純看直播用正式版
- **直播前導收割（v0.38.5，2026-10-24 從測試版移過來）**：管理版看直播＝前導端。**預設開、不用打指令**；管理版**一律不延遲畫面**；直播批次等 20 秒湊大批並標 `leader`、每 30 秒送心跳（`/v1/leader/beat`，帶收割權杖，不靠授權碼）。觀眾（正式版、延遲 45 秒）從 SubtitleRoom 撿譯文——R18 FP2 實測 93%。
  Console（切到 PitLingo（管理版））：`__pitlingo.leader()` **只看狀態**；`__pitlingo.leader(false)` 關、`leader(true, 20)` 開。⚠️ 同一個設定檔**不要同時開測試版**（兩個都疊字）；R18 FP2 開場就是兩個一起開出事

- **管理版只做管理版的事（2026-10-24）**：小視窗沒有登入、配對、授權、購買、新手導覽（`.customerOnly`＋`body.adminBuild`），最上面是「管理版」狀態卡（收割權杖、前導模式、延遲畫面固定關）。**身分只有收割權杖**：沒有權杖就不翻譯、不送心跳（sw.js `api()` 擋下），不退回用個人授權

### 語音辨識實驗室（測試版，v0.28.0）

回答三個問題：**聲音拿不拿得到、收割時能不能靜音或 2 倍速、「收割逐字稿 → 整份翻譯」準不準**。

1. **測試後端**（`f1zh-api-test`，不是正式後端）設好 `ASR_TEST_KEY`、`DEEPGRAM_API_KEY`、`ANTHROPIC_API_KEY`、`TOKEN_SECRET`（`--config wrangler.test.toml`，見 backend/README）
2. 在播放中的 F1TV 分頁（**開著英文 CC**）點擴充功能圖示 → 「🧪 語音辨識字幕」→ 填測試金鑰 → **開啟語音辨識實驗室**
   （擷取一定要從這裡開始：tabCapture 需要使用者在 F1TV 分頁上的手勢，實驗室分頁自己開不了）
3. 實驗室分頁：

| 區塊 | 做什麼 |
|---|---|
| ① 聲音拿得到嗎 | 即時音量表、近 60 秒音量曲線、影片狀態；自動判定：✅ 拿得到／❌ 播放中卻是空白（多半 DRM）／⚠️ 影片本身靜音／⏸ 暫停中 |
| ② 控制 | 監聽（接回喇叭，關掉＝靜音收割）、Chrome 分頁靜音、影片播放器靜音、播放速度（讀回實際速度，播放器擋下會顯示） |
| ③ 自動測試 | 依序切 7 種情況（基準、不監聽、分頁靜音、播放器靜音、1.5×、2×、2×＋不監聽），每種送一段辨識，比音量、每秒影片字數、與 CC 相似度，給出「能不能靜音收割／能不能 2 倍速」結論 |
| ④ 收割逐字稿 | 15 秒一段、重疊 2 秒、每段不翻譯只要逐字時間；重疊區以中點為界只留一份、依停頓與句尾標點斷句、時間換算成影片時間（暫停與倍速算得對，跳轉那一秒標「時間不明」） |
| ⑤ 整份翻譯 | 40 句一批送 `/v1/asr/test/translate`，不寫共用快取，顯示成本 |
| ⑥ 準確率 | 以官方 CC 為準逐分鐘算字錯率、估計時間偏移（可一鍵套用到 ④ 的時間校正） |
| ⑦ 儲存與播放 | 存到這台電腦、匯出 JSON、疊在影片上對齊播放位置檢查 |
| 除錯資訊 | 擷取狀態、每一段的音量／結果／辨識與往返耗時／字數／錯誤、事件記錄 |

⚠️ 組裝邏輯在 `src/test/asr-assemble.js`（純函式），`node tools/check-asr-assemble.js` 驗重疊去重、亂序、失敗段、倍速／暫停／跳轉的時間換算、字錯率。

1. 測試後端設定 `ASR_TEST_KEY` 與 `DEEPGRAM_API_KEY`（或 `OPENAI_API_KEY`），見 backend/README

## 補上官方漏掉的字幕（v0.25.0）

F1TV 的原生字幕偶爾會少一兩句，而使用者看到的是「PitLingo 沒翻」。
擴充功能會在**原生字幕空白、但依 VTT 推算此刻應該有一句**時，自己把那句補上。

| 成因 | 補得到嗎 |
|---|---|
| VTT 有這句，播放器沒畫 | ✅ |
| 太短，輪詢沒抓到 | ✅ |
| VTT 裡根本沒有（聽打員漏打） | ❌ 沒有來源 |

**做法是錨點，不是絕對時間。** cue 時間可能是分段相對秒數，直接對 `currentTime` 會在隨機時刻補出隨機句子。
原生字幕畫出某一句時記下播放位置，下一句在「錨點＋兩句 cue 起始差」出現——
同一個 VTT 檔案內的差值不論基準都準確；跨檔案只在偵測到絕對時間軸時採用。

不補的情況：暫停中、沒有譯文（不畫佔位字）、開著提前／延後、錨點超過 45 秒或被往回拖。

成效看 HUD 的「補字幕」一列，或診斷報告的「補上官方漏掉的字幕」區塊。
行為測試：`node tools/check-gapfill.js`（check-all 會跑）。

## 遠端設定（F1TV 改版時的救命索）

`sw.js` 啟動時會向後端要 `/v1/config`，內容是選擇器、contentId 規則、隱藏用 CSS。

- **選擇器是陣列，依序嘗試** —— F1TV 灰度推送期間新舊版同時存在，兩邊都能用
- 拿不到就用 `defaults.js` 的內建值，功能不會因為後端掛掉而中斷
- 快取 2 分鐘（原本 6 小時，導致熱修根本推不出去，見 handoff 8.1）
- `ccSelect`（v0.38.0）：播放器的字幕語言 `<select>`，自動開啟英文字幕用。遠端沒給時用內建的 `select.tm-ui-subtitleselectbox`

F1TV 改版時：**改後端 JSON → 幾分鐘內所有使用者恢復**，
而不是改程式碼 → 送審 → 等 1~3 天。

## ⚠️ 測試前必讀

**userscript 與擴充功能不能同時啟用**——兩個都會抓同一組字幕、畫出兩層疊字。
測試擴充功能時請先在 Tampermonkey 停用 PitLingo 腳本。

### 三條路徑，由快到慢

| 路徑 | 何時 | 延遲 |
|---|---|---|
| 共用快取命中 | 有人翻過這支 | **0 ms** |
| 整軌預抓完成 | 沒人翻過，但抓到字幕清單 | **0 ms**（整支先翻好，拖進度條也不漏） |
| Worker 攔截 | 清單取不到，但注入成功 | **0 ms**（提前約 50 秒，但只涵蓋播過的區段） |
| 逐句即時翻譯 | 以上都失敗 | 1~3 秒，會跳句 |

**最後一條是後備，不是正常運作模式。** 若診斷報告顯示停在「逐句模式」，
代表 Worker 注入失敗——那才是要修的問題。

### 診斷

擴充功能圖示 → **回報問題 → 傳送診斷資訊**（直接送到後端，回一組工單編號）。
報告包含預抓狀態、命中率、直播實測量測、事件時間軸，以及**最近 300 行詳細日誌**（v0.29.0 起，正式版也有——不必先打開任何開關）。測試版另外多「串流加密」一行（評估語音辨識用）。

Console（先切到 PitLingo 環境）：正式版 `__pitlingo.diag()` / `events()` / `peek()` / `state` / `hud()` / `autoDiag()`；測試版另有 `debug()`、`live()`、`t.*`

#### 自動回報（量測直播用，**預設關閉**）

```js
__pitlingo.autoDiag(10)   // 播放中每 10 分鐘自動送一份，停止播放 90 秒後再補最後一份
__pitlingo.autoDiag()     // 只查狀態，不改狀態
__pitlingo.autoDiag(0)    // 關閉
```

為什麼要有：提前量與中文落後**只存在使用者的瀏覽器裡**，後端看不到。
2026-09-23 那場直播後端側的數字全部拿到了，擴充功能側整場空白——賽後沒有人記得按按鈕。

⚠️ **預設關閉，設定頁上不存在這個開關。** 隱私權政策承諾「診斷資訊只在你按下傳送時才送出」，
客戶端永遠不會自己上傳任何東西。計時只算**實際播放的時間**（暫停或切到背景不累積）。

自動送出的那幾份存在另一個前綴，**不寄信、不進客訴清單、不算進每日彙報的工單數**；
後台「問題回報」勾「看自動回報」才看得到。

### 詳細日誌印到 Console（只在測試版）

正式版的詳細日誌只進診斷報告。測試版可以即時印出來：

```js
__pitlingo.debug(true)     // 立即生效，不用重整（只在 dist/pitlingo-test）
```

開啟後會印：

- 每一句偵測到的字幕，以及**是 observer 還是輪詢抓到的**
- 每一次本機快取命中／未命中
- 每一個送出的批次（內容、句數、耗時、回覆率）

詳細日誌**不寫進事件時間軸**——時間軸只有 400 筆，被逐句訊息灌爆就看不到真正的狀態變化了。

### 顯示延遲怎麼判讀

診斷報告的「顯示延遲的歸因」區塊回答一個問題：**這 0.5 秒有多少是我們造成的**。

| 看到什麼 | 意思 |
|---|---|
| observer 佔比高、繪製耗時個位數 ms | 我們幾乎沒加延遲，剩下的來自 F1TV 自己畫字幕的時機 |
| 輪詢佔比高 | observer 沒在作用，最壞會加一個 `POLL_MS` |

**先看這兩個數字再決定要不要調輪詢間隔**，不要憑感覺調。

### 字幕時機微調怎麼判讀（v0.16.0）

設定頁的「字幕時機」有兩個方向，難度完全不同：

| 方向 | 上限 | 機制 | 什麼時候有效 |
|---|---|---|---|
| 延後（往左） | **3 秒** | 單純 `setTimeout` | **任何情況**，包含直播 |
| 提前（往右） | **2 秒** | 需要 VTT 的 cue 時間軸 | 只有重播、且校準通過 |

上限刻意不對稱：延後設多少就是多少；提前依賴推算出來的基準，誤差會直接變成錯位的字幕。

**校準怎麼判斷可不可信。** 我們不解析 `X-TIMESTAMP-MAP`（決策 4.1 避開的那條路），
而是記錄「DOM 顯示那一刻的 `currentTime` − 該句的 cue 時間」當樣本。
關鍵在於**這批樣本的四分位距（IQR）**：

| IQR | 代表 | 行為 |
|---|---|---|
| 遠小於 1 秒 | cue 寫的是絕對時間，差值是播放器畫字幕的固定延遲 | 啟用提前 |
| 幾十～幾百秒 | cue 寫的是**分段內相對時間**，差值等於分段起點、隨播放增長 | **判定不可用，退回只延後** |

F1TV 用哪一種寫法我們沒有實測過——這個閘門的意義就是**兩種都不會出錯**。

**判斷結果不是黑箱**：診斷報告的「字幕時機微調」區塊會印出設定值、實際生效值、
樣本數、離散度；設定頁在拉動滑桿時也會直接問播放中的分頁「現在真的生效了嗎」。
使用者說「調了沒感覺」時，先看這兩處，不要用猜的。

**換影片會自動回到 0。** 它補的是「這一支影片的偏差」，不是長期偏好——
字級與位置才是長期偏好，那兩項刻意不重設。

**「字幕停留上限」已不是設定項**，改成固定 7 秒（`HOLD_MS`）。
自從疊字改成跟著原生字幕一起收掉之後，那個計時器在正常播放時永遠不會觸發，
放在設定頁上只是一個調了不會有反應的旋鈕。
